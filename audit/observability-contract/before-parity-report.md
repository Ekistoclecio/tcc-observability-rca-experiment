# Before parity audit — Common Observability Contract v1

Source: existing full-run RAW snapshots in `audit/results/datasetA|B/`, from the previous integration battery. No new experiment was run for this before-audit. Detailed machine inventories in `before-metrics.json`, `before-logs.json`, and `before-traces.json` were generated by `scripts/experiment/observability_contract_audit.py`.

## Native RAW inventory

| Signal | A | B | Audit finding |
|---|---:|---:|---|
| Prometheus samples | 22,980 | 214,920 | B has 9.35× samples and 90 native metric names vs A's 3 |
| Prometheus series | 171 | 1,592 | Majority of excess B series are runtime, SDK/exporter, and automatic instrument families |
| Loki records | 12,448 | 10,710 | Counts are not equalized; A has more records in this snapshot |
| Unique Jaeger trace IDs returned | 731 | 2,192 | Raw B includes substantial extra automatic/noise traces |
| Unique Jaeger spans returned | 15,205 | 16,916 | Raw B has 1,711 additional spans before contract filtering |
| Explicitly correlated Loki records | 0 | 10,710 | B records expose native trace_id and span_id; A records do not |

`before-traces.json` preserves native span names, kinds, tag/attribute keys, instrumentation scopes when present, and parent-reference counts. The historical contract-normalized view originally mapped both scenarios to the same 273 logical `(service, operation, kind, target)` concepts, 611 traces each, and 15,085 spans A / 15,080 spans B. However, a later audit found that Jaeger process IDs (`p1`, `p2`, ...) are scoped to each service-search response and can be reused. The old global merge could therefore assign some spans to the wrong service. These historical service-level logical counts are retained as evidence of the old snapshot but are not treated as reliable parity proof. This merge defect was fixed for the new F1/F4/F5 captures. The previous report's literal-name comparison was also misleading.

## Differences classified from evidence

| Difference | Classification | Evidence/decision |
|---|---|---|
| B `telemetry.sdk.*`, JVM, .NET, ASP.NET/Kestrel, exporter/SDK metrics | `NOISE` | Present in 90-name B inventory, absent in A, not needed for the defined fault evidence; removed at OTel Collector metric pipeline allowlist |
| A custom RED names vs B OTel/semantic names | `REPRESENTATION_DIFFERENCE` | Normalize to common concepts while preserving native names for audit |
| A has frontend route RED and recommendation→catalog client RED; old B snapshot lacks those concepts | `DIAGNOSTIC_COVERAGE_DIFFERENCE` | Explicit B OTel request/duration instruments are being added at those logical boundaries |
| A records Redis failure outcome; old B Redis operation metric lacked a common outcome dimension | `DIAGNOSTIC_COVERAGE_DIFFERENCE` | B Redis operation metrics now include `outcome=success|error`; standalone duplicate error counter is excluded |
| B native trace IDs, span IDs, parent IDs, and log correlation | `EXPECTED_CORRELATION_DIFFERENCE` | Retained as the experiment treatment; never copied into A |
| B's automatic health, scrape, and exporter spans | `NOISE` | Filtered by fixed span/peer attributes and the static logical operation catalog |

## Audit limits

This is a code-and-snapshot audit, not an after-change runtime validation. The new instruments, cAdvisor source, Collector filtering and reduced Dataset must be verified with the requested F1/F4/F5 smoke runs. In particular, exact values/counts can differ because scrape/export timing is asynchronous; acceptance is based on shared logical concepts and equal source semantics, not numerical equality.
